Welcome to your SkillSwap tutorial

You are about to build a real campus product — not a homework mockup that lives only on your laptop. By the end of this guide, SkillSwap will be live on the internet, and anyone with the link can use it.

1.1 You do not need to write the code yourself

You are a business student. You have never written code before. That is exactly who this tutorial is for.

You will not memorize syntax or fight a blank file. You will direct an AI assistant in Cursor: describe what SkillSwap should do, review what it builds, and ask it to fix problems in plain English. Think of yourself as the founder and product manager. Cursor is the engineering intern who types quickly and never gets tired.

What “done” looks like

A working SkillSwap site where students create accounts, list skills they can offer and skills they need, post help requests and skill offers, and find complementary matches — hosted online for free.

1.2 What you are building

SkillSwap is a university-wide platform that helps students find other students with the skills they need — and offer their own skills in return. Every student can be a helper and a requester at the same time. There are no separate roles.

College students already ask friends, classmates, or people in their major for help. That keeps talent trapped inside small networks. SkillSwap opens the bulletin board to the whole university: a Business student who needs presentation design can find an Engineering student who loves making slides — and maybe that same Engineering student needs Python, which the Business student can teach.

1.3 Understanding dynamic web apps

Before you click any installers, you need a mental model. Software feels mysterious only when you do not know where things live. Once you know that, every later step will make more sense.

What is a web app?

A website is mostly a brochure. A restaurant menu page shows the same dishes to everyone. You read it, maybe click a phone number, and leave. Nothing is saved about you.

A web app is a tool. Google Docs is a web app: you sign in, create documents, and they are still there tomorrow. SkillSwap is a web app because students create accounts, save profiles, post requests, and come back later to see matches.

The difference is state — remembered information. Your app has to remember Maya’s Python offer even after she closes her laptop.

The client-server model

Imagine a restaurant. The dining room is where guests sit, read the menu, and place orders. The kitchen stores ingredients and prepares food. Guests never walk into the kitchen. They talk to a waiter, who carries the order back and returns with a plate.

Web apps work the same way:

  • Frontend (the client) = the dining room. It is what students see in the browser: buttons, forms, the Discover feed, skill pills.
  • Backend (the server) = the kitchen. It stores profiles, posts, and login information. Users never see it directly.
  • API = the waiter. It carries a request (“show me open Excel offers”) from the frontend to the backend, then brings the answer back.

For SkillSwap, you can also picture a campus bulletin board. Discover is the board students walk up to. Supabase is the student-life office that keeps every flyer on file so the board is not empty when someone new walks in.

Why do you need both?

Data persistence. If Maya’s help request lived only in her browser, it would vanish when she closed the tab. Alex would never see it. The backend stores it permanently.

Multiple users. Maya and Alex need to look at the same set of posts. That shared truth has to live in one central place — the database — not on each person’s phone.

Security. You do not want a student to quietly edit someone else’s profile or delete another person’s request. Permission checks happen on the backend, where users cannot tamper with the rules. In Supabase those rules are called Row Level Security (RLS): tiny policies that say “you may only change rows that belong to you.”

What this means for SkillSwap

  • The frontend will be built with React through Next.js — a popular way to build interactive pages.
  • The backend will be Supabase — a service that already gives you a database and user accounts. You are not building a kitchen from plywood.
  • Students log in with an email one-time code (a 6-digit code), so nobody has to invent and remember a password.

Five tools. Each one has a job. You do not need to master them — you need to know why they exist.
